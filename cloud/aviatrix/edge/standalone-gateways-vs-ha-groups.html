Edge sites are easier to operate as standalone gateways than as HA groups

The short version

Edge gateways deployed at a site as an HA group have an operational limit. When the primary gateway has to be re-onboarded, the HA gateway's transit attachment also has to be deleted, and the whole site goes down. The recommended design is to deploy Edge as standalone gateways, so each gateway can be rebuilt without taking down its partner.

Details marked to be validated below have not been confirmed yet.

Background

The Edge documentation lists two HA group modes: active-active and active-standby. In a group deployment, a primary and an HA gateway are managed together under one site.

The problem

  • A primary gateway that has an issue may need to be re-onboarded.
  • If the pair is deployed as a group, the HA gateway's attachment to the transits also has to be deleted, which takes the site down.
  • With standalone gateways, the primary could come down while the other gateway stays up.

Why groups are hard to operate

  • The primary gateway is the constraint. Deleting, redeploying or rebuilding the primary requires doing the same to the HA gateway, so the site takes an outage.
  • An image upgrade of the primary gateway in a gateway group means bringing the HA gateway down as well.
  • The image itself is not the issue. The rebuild is.

Design options considered

Option Notes
Active-active group Gateways managed as one unit. Rebuilding the primary affects the HA gateway.
Active-standby group Same group management limitation as active-active.
Standalone gateways Selected design. Two independent Edge gateways per site, sharing a site ID, with ECMP from the transit.

Selected design: standalone gateways

  • Deploy two independent Edge gateways at each site and give both gateways at a site the same site ID. Each gateway is onboarded and attached to the transits on its own.
  • The transit load shares traffic across both gateways at a site with ECMP, because gateways that share a site ID are treated as one party.
  • Either gateway can be re-onboarded, rebuilt or upgraded while the other keeps carrying traffic.

Trade-offs and caveats

  • Gateways sharing a site ID run active-active. ECMP is performed within a site, not across sites, so gateways at different sites do not get ECMP between them.

To be validated:

  • That standalone gateways sharing a site ID get transit-side ECMP in the version in use.
  • Whether the underlay or connectivity provider changes the routing design.
  • The exact downtime behavior when deleting the primary or the HA gateway in each option.

Migrating from a gateway group to standalone gateways

This is a proposed high-level approach and is to be validated. Each gateway is replaced one at a time so the site keeps carrying traffic.

  1. Bring down the HA gateway in the gateway group.
  2. Redeploy that gateway as a standalone gateway.
  3. Fail over traffic to the new standalone gateway.
  4. Bring down the primary gateway.
  5. Rebuild the primary gateway as a standalone gateway.

To be validated:

  • That BGP over LAN and any other configuration on the gateway group is replicated to each new standalone gateway before traffic moves.
  • The procedure and version requirements for removing the primary gateway, since a primary with peerings or connections cannot be deleted.
