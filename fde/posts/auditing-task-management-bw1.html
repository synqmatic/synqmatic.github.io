About this series. This is a live, anonymized case study of running the AI FDE process with a real team. We'll call the company Company X and the team Team T. We're working through the process in order (audit, judgment, build, eval, deploy, observe), starting with the small base workflows that Team T's main workflows are built from. Details are generalized on purpose, and nothing here names a company, customer or product.

Why start with base workflows

Team T's primary workflows are not single things. Each one is assembled from smaller workflows that run underneath it: capturing work, tracking it, following up. If those foundations are shaky, the primary workflow inherits the problem, and any intelligence we add on top just makes the shakiness faster.

So before touching the primary workflows, we audit the base ones. We'll label them BW1, BW2 and so on. BW1 is task management.

The setup

The audit is the first stage of the process. Its job is to describe how the work really happens, exceptions included, before anyone decides what to automate. The documented process is rarely the real one, so the audit leans on how people actually work, not on what the procedure says.

This post covers the full audit of BW1, start to finish. Where we don't know something, we say so instead of guessing.

How tasks arrive

Work reaches Team T through four kinds of channel:

  • Email
  • Chat
  • Meetings
  • Calls

That is already a finding. One workflow with four front doors means four formats, four levels of detail, and four ways for a request to get lost or arrive half-specified.

How it runs today

Once a task arrives, the path is simple:

  1. The task is created in the team's task management tool, which we'll call R.
  2. It is matched to a category, using the category descriptions.
  3. It is managed in R until it is done.

Two decisions are folded into that path.

Is it ours? If a task fits none of the categories, it is not Team T's responsibility and is handed to another team. That is the one formal exception route.

Whose is it? Each team member is assigned to specific customers. When a task comes in for one of those customers, it belongs to that member, who owns it end to end: creating it, chasing missing details, splitting it into subtasks and tracking the time. There is no handoff inside the team. The task always stays with its owner, and if the owner is away, Team T's manager follows up on it.

Where it strains

None of these are failures. They are the places the audit looks hardest.

  • Category overlap. The category definitions are clear, but real tasks often fit more than one. The assigned member decides using their own judgment. The open question is whether every member resolves an overlap the same way. If they do not, that is not an exception to encode. It is a policy question to settle first.
  • Subtasks stall the workflow. When a task needs several subtasks, they get created and the other tasks in the same workflow stall behind them.
  • Meeting capture. Tasks from meetings and calls are captured either from memory or, for most calls, from a recording or transcript. Memory-only capture is the weakest path, because anything forgotten never becomes a task.
  • One owner carries everything. The same person handles creation, missing details, subtasks and time tracking for their customers. That keeps accountability clear, but it concentrates the overhead and makes the manager the only fallback.
  • No standard process. Team T has no standard way to create tasks. Company X has approved one AI assistant, and members use it in different ways. This is sanctioned but unstandardized use, not shadow AI. It tells us the team already sees value here, and that each person has built their own method.

The neighbours

The audit looks one step upstream and one step downstream, even though neither is being rebuilt. For a base workflow, both are thin.

Upstream is the communication itself: an email, a chat message, a meeting or a call. Team T does not control its format or quality, and nothing structured exists until a person turns it into a task.

Downstream is the work the task describes. It is done by the same person who owns the task, which couples the two more tightly than it looks. Time spent capturing and categorizing comes out of the same time used to do the work, and how complete a task is when created decides how much chasing happens later.

Where a queue could re-form. If capture got faster and tasks came out more complete, more of them would reach the owner's work queue sooner. We would expect the bottleneck to move to the owner's capacity, not disappear. That is a prediction, not an observation.

Baseline

Unmeasured. One team member's rough estimate is 2 to 3 hours a week spent managing tasks, varying with how much detail each task carries and how much gets documented. That is one person's recollection, not a measurement, so treat it as an order of magnitude only. Nobody measures capture time separately, the number of tasks per member per week, or how often a task is missed, and there is no practical way to capture that now. Over a year, 2 to 3 hours a week comes to roughly 100 to 150 hours per member (an estimate). That is the ceiling on what could be recovered, since only part of the work is something a system could take over.

Without a measured baseline, any future claim about time saved rests on a recollection. A measured baseline, or a proxy measure, should replace the estimate before anything is built.

Score and risk tag

The audit scores each candidate from 1 to 5 on six signals. These scores come from interviews, not measurement, so they are provisional.

SignalScoreWhy
Volume and frequency4Recurring work across every customer, but actual volume is unmeasured
Repetitiveness4Same basic shape each time (capture, categorize, create), though sources vary
Unstructured language5The input is emails, chat messages and call transcripts
Judgment level4Category matching is pattern-based, with overlap cases that need a call
Data availability4Emails, chat and most call transcripts are reachable; memory-only capture is the gap
Error tolerance4Internal work, and a wrong category is cheap to fix

Total: 25 of 30, provisional. With one workflow scored, there is nothing to rank it against yet. The number becomes meaningful once BW2 is scored, and there is no pass mark.

Risk tag: green. The process and the tool are both internal, the stakes are low, and a wrong output is recoverable. One thing to confirm: the source material (customer emails, call transcripts) may contain customer information. Because Company X's approved AI tool is already in use for this, it is probably covered, but it should be checked.

Where the audit lands

BW1 is a worthwhile candidate: recurring, language-heavy, pattern-based and low risk. It moves on to the judgment stage. Two open items travel with it:

  • The baseline is a working estimate. It should be replaced with a measurement before anything is built, so later results have something solid to be compared against.
  • Category decisions need checking for consistency across team members. If they differ, the policy has to be settled before anything is encoded.
