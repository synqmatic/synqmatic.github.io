Eval Design for Base Workflow 1: How Would We Prove the Category Decision?

About this series. This is a live, anonymized case study of running the AI FDE process with a real team. We'll call the company Company X and the team Team T. We're working through the process in order (audit, judgment, build, eval, deploy, observe), starting with the small base workflows that Team T's main workflows are built from. Details are generalized on purpose, and nothing here names a company, customer or product.

Where we left off

Post 2 split Base Workflow 1 (BW1, task management) into nine steps. Two use a model: drafting the task from a source, and proposing a category. One is a human approval, where the owner reviews the draft and category before anything is written. The category step is where a model's judgment matters most, and we have not yet checked whether team members resolve category overlaps the same way.

The eval stage

An eval turns a system that can give different answers on different days into evidence a peer can check. It has two parts. Design decides what counts as a test case and how each run is graded. Running feeds the cases through the real system and counts the results. Running needs a build, and BW1 is not built yet, so this post covers design only. It contains no pass rates.

What we grade

We grade the two model steps: the draft and the category proposal. We do not grade the owner's judgment. The owner remains the quality control at the approval step, and the eval checks that what reaches the owner is correct.

Each run is graded on four criteria: it used the right data, it followed the required steps, its output matches what an experienced team member would produce, and it is safe to act on without review. These can come apart. A draft can match what the owner would have written and still be unsafe to act on, for example if it attached the task to the wrong customer.

Five case types for BW1

Fifty runs of the normal case prove very little, so coverage across case types matters more than volume. These are the five types as they would look in BW1.

Case typeWhat it looks like in BW1Expected behavior
Normal caseA clear email or call transcript for one customer, one obvious category, complete detailsCorrect draft and category, passed to the owner for review
Edge caseA task that fits two categoriesProposes one category and flags the overlap. Graded on flagging, not on matching a single right answer, until the policy question is settled
Incomplete informationA source that leaves out details the task needsFlags what is missing and does not guess
Ambiguous requestA message that may or may not be a task, or a thread with several requestsAsks the owner to decide instead of creating a task
High-risk actionA task that fits no category and needs a handoff to another team, or a source where the customer match is unclearSurfaces it to the owner. Never routes or writes on its own

A correct escalation counts as a pass. A system that recognizes incomplete information and hands it back behaved as designed, and grading that as a miss would train us to build something that guesses. BW1 is tagged green and every write happens after the owner approves, so the high-risk set is small. It still needs cases, because it is where a wrong output costs the most.

Where the test cases come from

The starting point is the task history: past sources paired with the task that was created and the category the owner chose. Each pair gives a checkable answer. The method calls for 30 to 50 real past cases spread across the five types. That is a target, not something we have.

The set should eventually carry the choices of more than one team member. A set built from one person's calls tests that person's taste, and the first colleague who disagrees will stop trusting it.

There is a built-in gap. Tasks captured from memory leave no source behind, and tasks that were forgotten never became tasks at all. History cannot test either one.

Breaking the category decision into checks

"Is this the right category" looks subjective, but most of it splits into questions with yes or no answers:

  • Is the proposed category one of the defined categories?
  • Does it match the category the owner chose?
  • When a second category also fits, did the system flag the overlap?
  • When none fits, did the system say so instead of forcing a match?

The draft splits the same way: the right customer is named, every request in the source appears in the draft, and nothing appears in the draft that the source does not support. What is left after these checks is the residue a person has to judge. We capture the owner's corrections at the approval step as data, add each corrected case to the set, and re-run the whole set after any change, because a fix for one case often breaks another.

The report and its operating rules

The eval report gives a count of passed runs out of graded runs, with failures grouped by reason and each failure keeping its evidence. A single percentage would hide the reasons. The report also states three operating rules: a confidence threshold below which the system escalates, escalation of high-risk actions regardless of confidence, and the current readiness stage.

We have not set a threshold. Without results, any number would be a guess. The expected first readiness stage is shadow mode with the owner reviewing every task.

What we do not know yet

  • Whether the task history links each task back to its original source. Unknown.
  • How many usable past cases exist. Unknown.
  • Whether team members resolve category overlaps the same way. If they do not, the edge cases have no single right answer.
  • The confidence threshold. Not set.
  • Any pass rate. Nothing has been run.
