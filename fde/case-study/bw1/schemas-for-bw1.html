About this series. This is a live, anonymized case study of running the AI FDE process with a real team. We'll call the company Company X and the team Team T. We're working through the process in order (audit, judgment, build, eval, deploy, observe), starting with the small base workflows that Team T's main workflows are built from. Details are generalized on purpose, and nothing here names a company, customer or product.

Where we left off

Post 4 laid out a plan for the first Base Workflow 1 (BW1, task management) script and listed what each run record would hold in a single sentence. This post fixes those structures before any code is written. Nothing is built yet, so every field below is a proposal, and there are no results.

The stage

In the build stage, a schema is the agreed shape of the data that passes between steps. A defined shape lets the script reject malformed model output instead of passing it on. It also lets the eval grade a run field by field, which is how Post 3 broke the category decision into yes or no checks. We settle the structures first because the script, the eval and the run records all depend on them.

Rules for every schema

  • Every field the model fills can be empty. A model forced to fill every field will invent values, and an empty field is a reported gap the owner can see.
  • Output that fails validation is rejected, logged as failed, and sent to the owner. It is never passed to the next step.
  • Each schema carries a version number, so old records stay readable after the structure changes.
  • The category definitions, customer assignments and required-field list are inputs, not part of any schema. Changing one does not change the structure.

Model output

BW1 has two model calls. The first drafts the task from the source.

Draft fieldMeaning
titleA short task title
descriptionWhat needs doing, in plain language
customer_as_writtenThe customer as named in the source, before any lookup
requested_actionThe action being asked for
detailsOther facts the source states, such as dates or systems involved
unclear_pointsThings the source leaves ambiguous
evidenceThe part of the source each field came from, so the owner can check it

The second call proposes a category.

Category fieldMeaning
proposed_categoryOne of the defined categories, or empty
also_fitsOther categories that could apply, which flags an overlap
none_fitsTrue when no category applies, which means a handoff
reasoningOne or two sentences the owner can check
confidenceThe model's own estimate, from 0 to 1

Owner decision

FieldMeaning
actionApprove, edit or reject
final_draft, final_categoryThe values that will be written
editsEach changed field with its original and final value
reasonAn optional note on a rejection
decided_by, decided_atWho decided and when

The edits field matters most. It is the correction data that feeds the eval set.

Run record

FieldMeaning
schema_versionThe version of this structure
run_id, started_at, finished_atIdentity and timing
statusCreated, rejected, escalated or failed
customer, ownerAs resolved by the lookup
sourceThe type (email, chat, meeting or call), a reference and the text used
inputs_usedIdentifiers for the assignments, category definitions and required fields in force
model_callsFor each call: the step, the model name, the prompt, the response, and whether it passed validation
checksResults of the lookup, the completeness check and the write
escalationThe step and reason, when the run stopped early
decisionThe owner decision above
resultThe identifier of the created task, when one was created

The inputs_used field is what lets someone reconstruct a run later. Without it, a changed category definition would make an old run impossible to explain.

What may carry over to other workflows

We expect the outer shape of the run record to repeat: identity, timing, status, model calls, escalation and the approval checkpoint. The model output schemas and the contents of the owner decision are specific to BW1. With one workflow, this is a guess. We will treat the outer shape as provisional and check it when a second workflow is built.

What we do not know yet

  • Whether the model's own confidence value is reliable enough to set an escalation threshold. The eval will show this. Unknown.
  • Which fields owners will edit most. Unknown until real runs.
  • The required-field list and the category definitions as inputs. Not yet specified here.
  • Whether the outer shape of the run record fits other workflows. Unknown.
  • Where run records are stored and who can read them. They contain source text, so they raise the same data-rules question as the sources.
