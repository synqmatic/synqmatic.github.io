About this series. This is a live, anonymized case study of running the AI FDE process with a real team. We'll call the company Company X and the team Team T. We're working through the process in order (audit, judgment, build, eval, deploy, observe), starting with one of Team T's primary workflows, the work the team actually needs done. The audit of that workflow shows which smaller base workflows it depends on, and those get their own posts. Details are generalized on purpose, and nothing here names a company, customer or product.

Where we left off

Post 3 designed the eval for Primary Workflow 1 (PW1, new product reviews): five case types, four grading criteria, and test cases built from release source material that people label. It also noted that Team T will create a standardized release document, which defines a correct draft, and that running the eval needs a working version. This post covers that version. Nothing is built yet, so this is a plan, and it contains no results.

The build stage

The build stage turns the step allocation from Post 2 into running code. Two rules from the method apply from the first line: build on top of the tools the team already uses, and log a trace of every run. Deployment comes after the eval and starts in shadow mode.

What we plan to build first

One script for PW1, and no shared infrastructure yet. A setting on the script chooses the track, release or roadmap. Deterministic code handles the source material and the output file. A model is called only at the two judgment steps. At the approval step the script stops and waits for the team member's answer on the command line, which stands in for a real interface until one exists.

Because the release document is the same for every customer, one run covers one release, not one customer. The script does not send anything to customers. It produces an approved document for the team member to deliver.

Inputs and failure handling

The script needs three inputs: the source material for the run, the written statement of what is shareable, and the standard release document form. We will supply them by hand at first. PW1 reads no per-customer information, because the document is generic, so the full per-customer context file is not needed for this workflow.

Each exception from Post 2 gets a defined route: source missing or unreachable, a label the model is unsure of, too little shareable material, and a model call that fails. Each one goes back to the team member instead of being guessed. The script also checks its own output against a defined format and rejects anything malformed before it moves on. A transient failure is retried, and a failure that will not clear is reported.

Run records

Every run produces one structured record, saved as its own file. It holds the run ID and time, the track, the release or request, the inputs, each model call with its prompt and response, the labels, the draft, what the team member was shown, who approved and when, any correction and missed-item note, the final output and the run status.

The records have a second use. Corrections and missed-item notes captured at the approval step become new cases for the eval set. Plain local files are enough for now. Where the records live later is undecided.

What comes after the first script

Once more than one workflow runs as a separate script, we plan to consolidate them behind one shared server, then put a front end on top. The front end would be a chat app first, because it is where the team already works and it suits an approval step. A web app would come later, only if a workflow needs structured input a chat app handles poorly. We are not building the shared parts first, because with one workflow we would be designing them around assumptions we cannot check.

Deployment plan

PW1 starts in shadow mode. The script runs next to the current process, the team member keeps working as today, and the script's output is compared, not used. The manual path stays open, and the team member can see the full trace of each run. Releases come about quarterly (estimate), so a real comparison happens about once a quarter. Until then, shadow runs use the constructed cases from Post 3. We also need to agree in advance what sends PW1 back to shadow mode. That threshold is not set.

What has to happen before we build

  • Define the standardized release document. The draft form and the eval both depend on it.
  • Write down what is shareable, and check whether team members draw the line in the same place. If they do not, settle the policy before encoding it.
  • Confirm that the source material is covered by the approved AI tool's data rules. Until then, first runs use only material we can verify is cleared for the tool.
  • Replace the baseline estimates with a measurement.
  • Write the expected time saved as a prediction. We have estimates but no prediction yet, and the method asks for one before anything is built. We expect the end-to-end time to move less than the drafting time, because delivery stays with a person.
  • Label a first small set of cases, which the eval needs before it can run.

What we don't know yet

  • The measured baseline. Unknown.
  • Whether the data rules cover the source material. Unknown.
  • Where the source material lives and how a script would read it. Unknown.
  • Cost per run and time per run. Not measured, since nothing has run.
  • Where run records should live beyond local files. Undecided.
  • The threshold that sends PW1 back to shadow mode. Not set.
