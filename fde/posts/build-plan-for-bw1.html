About this series. This is a live, anonymized case study of running the AI FDE process with a real team. We'll call the company Company X and the team Team T. We're working through the process in order (audit, judgment, build, eval, deploy, observe), starting with the small base workflows that Team T's main workflows are built from. Details are generalized on purpose, and nothing here names a company, customer or product.

Where we left off

Post 3 designed the eval for Base Workflow 1 (BW1, task management): five case types, four grading criteria, and a test set drawn from the task history. It also noted that running the eval needs a working version. This post covers that version. Nothing is built yet, so this is a plan, and it contains no results.

The build stage

The build stage turns the step allocation from Post 2 into running code. Two rules from the method apply from the first line: build on top of the tools the team already uses, not beside them, and log a trace of every run. Deployment comes after the eval and starts in shadow mode.

What we plan to build first

One script for BW1, and no shared infrastructure yet. Deterministic code handles the lookups, checks and writes. A model is called only at the two judgment steps. At the approval step the script stops and waits for the owner's answer on the command line, which stands in for a real interface until one exists.

Inputs and failure handling

The script needs three inputs: the customer assignments, the category definitions and the list of required fields. We will supply them by hand at first. The full per-customer context file is not built, and each script should take only the slice it reads.

The exceptions from Post 2 each get a defined route: customer not found, source missing or unclear, no category fits, missing details, and a failed write. Each one goes back to the owner instead of being guessed. The script also checks its own output against a defined format and rejects anything malformed before it moves on. A transient write failure is retried. A failure that will not clear is reported to the owner.

Run records

Every run produces one structured record, saved as its own file. It holds the run ID and time, the customer, the inputs, each model call with its prompt and response, intermediate outputs, what the owner was shown, who approved and when, any correction the owner made, the final output and the run status.

The records have a second use. Corrections captured at the approval step become new cases for the eval set. Plain local files are enough for now. Where the records live later is undecided.

What comes after the first script

Once several workflows run as separate scripts, we plan to consolidate them behind one shared server, then put a front end on top. The front end would be a chat app first, because it is where the team already works and it suits an approval step. A web app would come later, only if a workflow needs structured input a chat app handles poorly. We are not building the shared parts first. With only one workflow, we would be designing them around assumptions we cannot check.

Deployment plan

BW1 starts in shadow mode. The script runs next to the current process, the owner keeps working as today, and the script's output is compared, not used. The manual path stays open, and the owner can see the full trace of each run. We also need to agree in advance what sends BW1 back to shadow mode. That threshold is not set.

What has to happen before we build

  • Replace the baseline estimate with a measurement.
  • Check whether team members resolve category overlaps the same way. If they do not, settle the policy before encoding it.
  • Confirm that the source material is covered by the approved AI tool's data rules. Until then, first runs use only sources we can verify contain no customer information.
  • Write the expected time saved as a prediction. We have a baseline estimate but no prediction yet, and the method asks for one before anything is built.

What we do not know yet

  • The measured baseline. Unknown.
  • Whether the data rules cover the source material. Unknown.
  • Cost per run and time per run. Not measured, since nothing has run.
  • Where run records should live beyond local files. Undecided.
  • The threshold that sends BW1 back to shadow mode. Not set.

What comes next
